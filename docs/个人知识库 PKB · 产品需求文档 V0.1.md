## 第零步：总纲（三个问题的回答）

### Q1 · 产品定义（两层结构）

**V0.1 层（本次交付）**：把「写下来」这件事的摩擦降到最低，并保证写下来的东西**一定找得回来**。三个动作各自独立、可单独使用，数据只有一份：

- **A 快速记录** —— 一个输入框，回车即存，不用先想分类
- **B 项目档案** —— 把散落的笔记归到「项目」下，形成一条时间线
- **C AI 检索** —— V0.3 才做；V0.1 用「搜索」把它的一半能力先兑出来

三者的关系是**同一份数据的三段**，不是三个模块：A 产生数据 → B 组织数据 → C 消费数据。V0.1 只交付 A 与 B，以及为 C 铺路的数据结构（`content_text` 搜索列、结构化标签关联）。

**长期层（架构愿景，V0.3，V0.1 不做）**：在已有结构化笔记数据之上引入**向量检索 + RAG 问答**，把「搜索」升级为「问答」——问「我上次怎么解决 Nginx 那个报错的」，系统直接给答案并附出处。前提是**数据先积累起来**，所以 V0.1 的首要任务不是智能，是让人愿意写。

### Q2 · V0.1 的成功观测（自用系统语境）

这是**单用户自用系统，没有 KPI、没有转化率、没有上线窗口**。唯一真实的验收标准是「我自己愿不愿意一直用它」，故指标改为**过程观测值**：

- **是否真的在用**：V0.1 交付后 14 天内，**日均新增笔记 ≥ 1 条**（低于此值说明记录摩擦仍然太高，是产品问题不是自律问题）
- **闭环是否跑通**：inbox 里的笔记**不会被永久积压** —— 任意时刻 `status=0` 的条数不超过新增总量的 30%
- **是否找得回**：随机抽 10 条已归档笔记，用搜索**一次命中**（标题或正文关键词）≥ 9 条
- **是否零维护**：V0.1 运行期内**不需要手工修数据库、不需要重建索引、不需要进制脚本**（自用系统最怕「要伺候」）
- **稳定性硬指标**：0 次数据丢失；笔记保存**不允许出现「以为存了其实没存」**

> 以上均为**观测值**，用于复盘与决定 V0.2 做什么，**不设目标值、不做考核**。

## 一、背景与目标（Why）

### 1.1 现状

前身「OSC 社团管理系统」于 2026-09-30 归档。该系统已完成 T1~T34（Vue 3 + Spring Boot 3 全栈、三档响应式外壳、Sa-Token 鉴权、MinIO 上传、富文本双重 XSS 清洗、Excel 导入导出、ECharts 看板），是一套**工程上已验证可用**的代码库，但**业务上已失去价值**（社团场景不复存在）。

同时，个人的知识管理现状是：想法记在聊天工具里、资料散在多个目录、技术笔记写在零散文件中，**没有一处可检索的沉淀**。已有工具（飞书文档、备忘录、笔记 App）的问题是：要么太重（要分类、要整理、要选模板）、要么太锁（数据在别人服务器、不能结构化检索、导出即残废）。

### 1.2 驱动力

1. **记录摩擦必须降到趋近于零**：只要「先想清楚放哪个目录」这个动作存在，记录习惯就会断。核心设计目标是把「写」和「分类」**在时间上解耦** —— 先无脑写进 inbox，之后再清理分类。
2. **数据必须自己完全掌控**：本机 / 局域网部署，MySQL + 本地文件存储，随时可备份、可迁移、可写脚本处理。
3. **工程底座已经现成**：OSC 的脚手架（统一返回体、全局异常、Sa-Token、MinIO、三档外壳、Sass 变量体系、MyBatis-Plus 约定）**已验证可用**，删除业务后即为干净的起跑线，无需从零搭。
4. **为 AI 检索预留结构**：V0.3 的 RAG 需要的是「干净的正文文本 + 结构化元信息」，所以 V0.1 必须**从一开始就把搜索列、格式、标签关联设计对**，避免后期回头洗数据。

### 1.3 系统定位声明

**PKB 不是笔记软件，是「个人外脑」的最小内核。**

- **它不做的**：不做协作、不做分享、不做多端同步账号体系、不做模板市场、不做花哨的块编辑器。**唯一用户是作者本人**，任何「为了别的用户」而增加的设计都是负资产。
- **它必须做好的**：**存得进**（零摩擦记录）、**找得到**（可靠检索）、**看得懂**（格式不漂、标签有结构）。
- **它与 OSC 的关系**：**只借工程脚手架，不借任何业务逻辑**。权限模型、数据模型、页面结构**全部重新设计**，不复用 OSC 的任何业务代码。OSC 的归档仓（`New-Management-System`）在本项目开发期间**只读参考**。

### 1.4 V0.1 非目标（明确不做）

多用户 / 注册 / 分享 / 协作 ｜ 版本历史 ｜ 回收站 UI ｜ 多角色权限矩阵 ｜ 导入导出界面（Excel / Markdown 批量） ｜ 看板 ｜ 公告 ｜ 反馈 ｜ 报名审核 ｜ 短信 ｜ 成员档案 ｜ 飞书集成 ｜ 上线部署（公网 / 多实例） ｜ RAG / 向量检索 / AI 问答 ｜ 模板与双向链接 ｜ 思维导图 / 白板 / 看板视图 ｜ 结构化块编辑器（Notion 式）。

> ⚠️ **保留但不启用**：FastExcel（`cn.idev.excel`）与 ECharts 封装代码**保留在工程内、不删不改不启用** —— 未来极可能用上（导出笔记、看知识增长曲线）。此为**用户明确拍板**事项。

## 二、用户与角色（Who）

### 2.1 使用端矩阵

单用户系统，无角色划分。唯一的「身份差异」是**首次部署前后的引导态**与**登录态**：

| 端 / 状态 | 说明 | 可访问范围 |
| :--- | :--- | :--- |
| 引导态（未初始化） | 数据库无账号 | 仅引导页（创建唯一账号） |
| 未登录 | 已初始化但无 token | 仅登录页 |
| 已登录 | 持有有效 Sa-Token | 全部功能 |

### 2.2 单账号原则（替代 OSC 的权限矩阵）

- **只有一个账号**，由**引导页**在首启时创建（输入手机号 + 密码，不触发强制改密）。
- **无权限矩阵**：`web/src/constants/roles.js` **整删**；路由守卫**只判两件事** —— 「是否已初始化」「是否已登录」，不做任何角色 / 能力判定。
- **无强制改密**：单账号的密码是本人自己设的，不存在「密码非本人选」场景，故强制改密逻辑**删除**（区别于 OSC）。
- **图形验证码保留**：登录仍需算术图形验证码（防暴力破解），此点与 OSC 一致。
- **可扩展性声明**：表结构允许未来加 `user` 行实现多用户，但 **V0.1 不做、不预留 UI、不写多用户逻辑**。

## 四、功能需求详述

> **阅读约定**：每张卡片的「数据要求」只写**字段级约束**；表结构权威定义见第六章。「关联」列出强耦合的功能卡。

### P-001 快速记录

**优先级**：Must ｜ **所属切片**：V0.1 第 5 / 9 片（后端 T5、前端首页入口 T9）

**用户故事**：作为使用者（US-1），我在任意时刻冒出一个想法，用**一个输入框 + 一次回车**把它存进系统，不需要先决定它属于哪个项目、贴什么标签。

**功能描述**：

- **入口**（两处，行为完全一致）：
  1. 首页顶部常驻输入框（桌面 / 手机均常驻，不随滚动消失）
  2. 笔记列表页的「新建」按钮（进入完整编辑表单，见 P-003）
- **极简流程**（首页输入框）：
  1. 聚焦输入框，输入标题或正文首句（**单行输入，不弹窗、不跳页**）
  2. 右侧格式切换按钮决定本次新建的格式（**默认 md**，见 P-004）
  3. 按 `Enter` → 立即创建一条 `status=0`（inbox）的笔记 → **toast 提示「已存入待整理」** → 输入框清空、焦点保留
  4. **不跳页、不打断**：使用者可以连续输入多条
- **输入内容的落库口径**：
  - 输入的文字**同时**作为 `title` 与 `content` 的初始值（`title` 取首行、`content` 存全文；首行之外的换行在极简单行输入框内不产生）
  - `content_text` 按 P-004 / 6.2 的规则同步生成
- **格式按钮行为**：点击在 md / html 之间切换，**只影响此后新建的笔记**，不改变任何已有笔记的格式；按钮状态在同一会话内保持（不因刷新丢失则记为体验目标，非硬性）
- **分支与异常**：
  - 输入为空 / 全空白 → 回车**不创建**，输入框轻微抖动提示（不弹错误框）
  - 保存失败（网络 / 后端异常）→ **保留输入内容**、toast 报错、允许重试（**绝不清空输入框**）
  - 输入超长（超过 `title` 字段容量）→ `title` 截断存入，**全文仍完整进 `content`**；截断需在实现方案中定阈值
  - 连击回车 → 前端需做**提交中禁用**，防止产生重复空笔记

**验收标准**：

- [ ] 首页输入框回车后，笔记列表与首页「待整理」列**立即可见**该条
- [ ] 创建成功后**页面不发生跳转**，输入框清空且保持聚焦
- [ ] 格式按钮切换后新建的笔记，`content_format` 与按钮状态一致
- [ ] 空输入回车不产生任何数据
- [ ] 保存失败时输入内容不丢失
- [ ] 连续快速回车 5 次，产生的笔记条数与有效输入次数一致（不重不漏）

**数据要求**：

- 写入 `note`：`title`、`content`、`content_format`（默认 `0`）、`content_text`、`status=0`、`pinned=0`
- **`content_text` 必须与 `content` 同步生成**（铁律 3，见 6.2）

**关联**：P-004（格式）、P-005（inbox 定义）、P-009（后续补附件）、P-010（首页入口）

### P-002 笔记列表

**优先级**：Must ｜ **所属切片**：V0.1 第 6 片

**用户故事**：作为使用者（US-4），我想按「全部 / 待整理 / 已归档 / 某项目 / 某标签」浏览我的笔记，并能在列表里一眼看出它是什么、什么时候写的。

**功能描述**：

- **入口**：外壳菜单「笔记」；首页状态条点击后带筛选条件跳入
- **列表项展示字段**：标题（空标题显示占位文案，如「（无标题）」）、正文摘要（`content_text` 截断，纯文本不渲染格式）、格式标识（md / html 徽标）、所属项目名、标签（最多显示 N 个，超出显示 `+n`）、状态（待整理 / 已归档）、置顶标识、更新时间
- **筛选**：状态（全部 / 待整理 / 已归档）、项目（单选）、标签（多选，AND 语义）
- **排序口径（冻结）**：`ORDER BY pinned DESC, updated_at DESC`
- **分页**：默认每页 20，滚动或翻页加载更多
- **行内操作**：点击整行进详情（P-003）；置顶 / 取消置顶；归档 / 取回（P-005）；删除（**V0.1 无回收站，删除为逻辑删除且需二次确认**）
- **分支与异常**：
  - 无数据 → 空状态引导（「还没有笔记，去首页写第一条」）
  - 筛选无结果 → 空状态 + 清除筛选入口
  - 笔记数量大（>1000）→ 需分页，**禁用一次性全量加载**
  - 长标题 / 超长标签名 → 省略号截断，不撑破布局
  - 手机端（<768）→ 卡片流，**无横向滚动**

**验收标准**：

- [ ] 默认列表按 `pinned DESC, updated_at DESC` 排序，置顶项恒在最前
- [ ] 四个筛选维度各自可用且可组合；切换筛选后分页重置为第 1 页
- [ ] 空标题笔记显示占位文案而非空白行
- [ ] 手机档（375px 视口）下无横向滚动条，列表为卡片流
- [ ] 删除操作有二次确认；删除后列表即时移除
- [ ] 归档 / 取回操作后，列表的筛选结果与状态标签同步更新

### P-004 双格式编辑

**优先级**：Must ｜ **所属切片**：V0.1 第 7 片

**用户故事**：作为使用者（US-8），我要写技术笔记（含代码块与表格），也要写排版讲究的富文本，两种我都要，但**一条笔记只用一种、不来回换**。

- `note.content_text`：由后端按格式分别生成（见 6.2）

### P-005 待整理闭环

- **批量（V0.1 边界）**：**V0.1 不做批量勾选归档**，逐条处理；如实际使用中确认痛点明显，列入 V0.2

  - `status` 非法值 → 后端拒绝

**验收标准**：

- [ ] 新建的笔记 `status=0`，出现在首页「待整理」列与列表「待整理」筛选下
- [ ] 归档后从「待整理」列消失，出现在「已归档」筛选下

- [ ] 归档时可以不选项目
- [ ] 状态条上的待整理数字随归档 / 取回即时变化
- [ ] 重复归档不报错、不产生脏数据

**数据要求**：

- 更新 `note.status`（`0` / `1`）与 `note.updated_at`

### P-008 搜索

**优先级**：Must ｜ **所属切片**：V0.1 第 10 片

**用户故事**：作为使用者（US-3），我记不住标题，只记得正文里出现过某个词，搜它就能找到。

- [ ] 手机档搜索框可用、结果列表无横向滚动

**数据要求**：

- 查询条件：`title LIKE ? OR content_text LIKE ?`（**不含 `content`**）
- `content_text` 的生成规则见 6.2；**索引口径见 6.4（T10 方案中定，倾向 V0.1 不建全文索引）**

**关联**：P-004（`content_text` 来源）P-002（结果列表样式）P-003（点进详情）

### P-009 附件

**优先级**：Must ｜ **所属切片**：V0.1 第 11 片

**用户故事**：作为使用者（US-5），我给笔记挂截图、PDF、表格文件，半年后还能一起找到并直接打开。

**功能描述**：

- **存储方式（冻结）**：MinIO（bucket `pkb`）；**库里只存对象 key**（`file_key`），读取时拼公开前缀
- **一条笔记可挂多个附件**（`attachment.note_id` 一对多）
- **支持类型（重要差异点）**：**不止图片** —— PDF / doc / xlsx / zip / txt 等常见文件都要支持
  - ⚠️ OSC 的 `ImageValidator` 是**图片专用**（魔数校验图片），**不能硬套**。通用上传需按**扩展名 + MIME 白名单**放宽，并对可识别类型做魔数校验
- **附件操作**：上传、列出（名称 / 大小 / 类型 / 时间）、下载 / 打开、删除
- **展示**：图片类可缩略预览；非图片类显示文件类型图标 + 文件名 + 大小
- **分支与异常**：
  - 超过大小上限 → 拒绝并提示上限（**上限值待拍板**：候选 20MB / 50MB）
  - 不在白名单的类型 → 拒绝并提示
  - 伪装扩展名（如文本改名成 `.png`）→ 魔数校验拦下（**可识别的类型必须校验**）
  - 上传中途失败 / 页面关闭 → 不产生半截记录；MinIO 里可能的残留对象由**孤儿清理**逻辑处理（`StorageCleanupService` 思路可复用，**V0.1 是否做清理 UI 待拍板**）
  - 删除附件 → `attachment` 逻辑删除，MinIO 对象是否同步删除**待拍板**
  - 删除笔记时其附件如何处理 → **待拍板**（倾向：附件一并逻辑删除，对象保留待清理）
  - MinIO 未配置 / 不可用 → 应用仍能启动（沿用 OSC 的降级约定），上传功能给出明确错误提示而非 500

**验收标准**：

- [ ] 可上传 pdf / xlsx / png / zip，均可下载并正确打开
- [ ] 库里 `attachment.file_key` 为对象 key，**不是完整 URL**
- [ ] 改名伪装的非法文件被魔数校验拒绝
- [ ] 一条笔记挂 3 个附件，详情页全部列出且可分别下载
- [ ] 超过大小上限时被拒绝且提示明确
- [ ] MinIO 不可用时后端能正常启动，上传接口返回业务错误而非 500
- [ ] 删除附件后列表即时移除

**数据要求**：

- `attachment`：`note_id`、`file_key`、`file_name`、`size`、`mime`、`is_deleted`
- MinIO bucket：`pkb`（应用启动时自动创建并设公开读）

### P-011 单账号登录

**优先级**：Must ｜ **所属切片**：V0.1 第 3 片

**用户故事**：作为唯一使用者，我首次部署时创建一个账号，之后登录进入系统。

**功能描述**：

- **引导态与引导页（首启）**：
  1. 系统检测是否有账号：无 → **任何路由都重定向到引导页**（`/init`）
  2. 引导页创建**唯一账号**：手机号 + 密码（+ 确认密码）
  3. 创建成功 → 跳登录页；**不触发强制改密**（本人自设密码）
- **登录**：
  1. 输入手机号 + 密码 + **算术图形验证码**
  2. 校验：验证码 → 账号存在 → BCrypt 比对 → 签发 **Sa-Token（Header 方式）** → 前端持久化 → 跳首页
  3. **验证码一次性作废**（与 OSC 一致）
- **登录守卫（只判两件事）**：是否已初始化、是否已登录。**不做角色 / 能力判定**（无权限矩阵）
- **分支与异常**：
  - 验证码错误 → 提示并刷新验证码
  - 密码错误 → 累计失败次数，提示
  - **连续失败 5 次 → 锁定 15 分钟**（沿用 OSC 口径）
  - 已初始化后再次访问 `/init` → 重定向到登录页（**不得二次建号**）
  - 后端重启 / token 失效 → 前端拦截器捕获未登录 → 跳登录页
  - 未登录直接输内页 URL → 弹回登录页
  - **忘记密码（自用系统特殊口径）**：V0.1 不做找回流程，**改为文档化的重置方式**（直接改库或提供一次性脚本），**具体做法待拍板**

**验收标准**：

- [ ] 空库首启，访问任意路由都落到引导页
- [ ] 引导页建号成功后跳登录页，**不要求强制改密**
- [ ] 已初始化后访问 `/init` 被重定向，**无法创建第二个账号**
- [ ] 正确手机号 + 密码 + 验证码可登录；验证码用一次后失效
- [ ] 密码连续错 5 次锁定 15 分钟，提示明确
- [ ] 退出登录后 token 清空，再访问内页被弹回登录页
- [ ] 登录成功 token 经 Header 返回并被前端持久化
- [ ] 前端代码中**不再存在** `constants/roles.js` 及其引用

**数据要求**：

- `user` 表**简化为单账号**：去掉 `role` / `department` / `duty` 等权限推导字段（**改表前需先确认 OSC 的 `user` 表哪些字段可删**，见 6.5）
- 密码：BCrypt 加密存储（`BCryptPasswordEncoder`，兼容 `$2b$`）
- 登录失败计数：Redis（沿用 `login:fail:{phone}` 思路，TTL 15min）
- 验证码：Redis（算术验证码答案，一次性）
- Token：Sa-Token，Header key **需定**（沿用 `osc-token` 还是改 `pkb-token`，见待拍板项）

**关联**：P-010（登录后落地页）

> ⚠️ 4 张表的结构与 3 条铁律**已冻结**；本章中标注「待拍板」的索引 / 约束细节，需用户确认后方可实施。

### 5.1 四张表（冻结）

| 表 | 关键字段 | 说明 |
| :--- | :--- | :--- |
| `note` | `id`, `title`, `content`, `content_format`(0=md/1=html), `content_text`, `status`(0=inbox/1=archived), `pinned`, `created_at`, `updated_at`, `is_deleted` | 一条笔记一种格式，新建选定后**不切换**，默认 md |
| `tag` | `id`, `name`, `type`(0=标签/1=项目), `color`, `sort`, `created_at`, `is_deleted` | 项目 = `type=1`；表允许多对多，UI 约束项目单选 |

### 5.2 三条铁律（冻结，改动需用户拍板）

1. **一条笔记一种格式** —— `content_format` 新建时选定、之后不切换、默认 md。
2. **项目 = `tag.type=1`** —— 表结构允许多对多，**UI 层约束为单个**；后端关联写入必须兜底（已有关联 `type=1` 时**替换而非新增**）。
3. **`content_text` 是搜索专用列** —— **搜索只打 `title + content_text`，永不打 `content`**。

### 5.3 排序与搜索口径（冻结）

- **排序**：`ORDER BY pinned DESC, updated_at DESC`
- **搜索范围（V0.1）**：只搜**标题 + 正文**；搜标签名留给后续版本
- **逻辑删除**：全表沿用 `is_deleted` + MyBatis-Plus `@TableLogic`；**所有查询默认带 `is_deleted=0`**

### 5.4 待拍板的数据层细节（T2 方案中定）

## 六、数据与字段决策

### 6.1 `note` 表

| 字段 | 类型（建议） | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| `id` | BIGINT | PK, AUTO_INCREMENT | — |
| `title` | VARCHAR(255) | NOT NULL | 空标题允许（UI 显示占位文案）；超长截断 |
| `content` | LONGTEXT | — | 原文；格式由 `content_format` 决定 |
| `content_format` | TINYINT | NOT NULL, DEFAULT 0 | `0=md` / `1=html`；**建后不可更新** |
| `content_text` | LONGTEXT | — | **搜索专用**；生成规则见 6.2 |
| `status` | TINYINT | NOT NULL, DEFAULT 0 | `0=inbox` / `1=archived` |
| `pinned` | TINYINT | NOT NULL, DEFAULT 0 | 置顶；**明确保留**，参与排序 |
| `created_at` | DATETIME | NOT NULL | — |
| `updated_at` | DATETIME | NOT NULL | 参与排序；**归类 / 取回会改变它** |
| `is_deleted` | TINYINT | NOT NULL, DEFAULT 0 | `@TableLogic` |

### 6.2 `content_text` 生成规则（搜索正确性的关键）

**铁律 3 的落地口径**：`content_text` 是**搜索专用列**，必须与 `content` 同步生成。

| 格式 | `content_text` 来源 | 处理要点 |
| :--- | :--- | :--- |
| `0=md` | `content` 原文 → **轻量去标记** | 剥 `#` / `*` / `-` / 链接语法 / 代码围栏，保留纯文本 |
| `1=html` | `content` → **jsoup `text()` 剥标签** | 得到纯文本，**不得残留标签名** |

**三条实现约束（红线）**：

1. **统一收口**：新增 / 更新笔记必须走**同一道**「写 `content` + 算 `content_text`」逻辑（Service 层），**禁止 Mapper 层散落写**——漏同步 = 搜索漏数据。
2. **md 去标记是必须的**：若 md 原文直接进 `content_text`，搜「项目」会误召回含 `# 项目` 的标记内容。**轻量去标记的具体规则（剥哪些符号、是否保留代码块内容）在 T5 方案中定稿**。
3. **搜索条件永不含 `content`**：任何搜索实现都只允许 `title` 与 `content_text` 参与匹配。

### 6.3 `tag` / `note_tag` / `attachment`

见 5.1 速览表；字段级类型与索引在 T2 数据层方案中定稿（受 5.4 待拍板项约束）。

### 6.4 格式与内容

- **格式不可切换**：`content_format` 在更新接口中**必须被显式忽略**（即使前端传了也不生效），并建议直接拒绝该字段的更新请求，避免「以为能改」。
- **XSS 清洗位置**：`html` 格式在**入库前**过 jsoup；展示前过 DOMPurify（前端）；**md 渲染产物同样过 DOMPurify**。

### 6.5 `user` 表简化

- 去掉权限推导字段：`role`、`department`、`duty`
- `activated_at`（OSC 用于「首登强制改密」判定）**用途需重判** —— 单账号无强制改密，该字段可能不再需要
- **改表前必须先核对 OSC `user` 表实际结构**，逐字段确认「可删 / 保留 / 改造」，**不得凭记忆删列**

## 七、非功能需求（NFR）

1. **自用优先（最高优先级）**：单用户、本机 / 局域网。任何为「多用户、公网、高并发」付出的复杂度都是负资产。**不引入不必要的中间件**（已有 MySQL + Redis + MinIO 即为上限）。
2. **性能（个人数据量语境）**：按**万级笔记**设计即可 ——
   - 列表 / 首页首屏 ≤ 1 秒
   - 保存笔记（含 `content_text` 计算）≤ 500 毫秒（后端）
   - 搜索响应 ≤ 500 毫秒（万级数据下 `LIKE`）
   - 搜索框输入防抖，**不得每敲一个字打一次全表**
3. **数据安全（自用系统最痛的点）**：
   - **绝不允许「以为存了其实没存」**：保存成功才提示成功
   - **`content_text` 必须同步**（铁律 3）；建议在 T5 加入启动自检或一次性修复脚本，用于修复历史漏同步数据（**是否纳入 V0.1 待拍板**）
   - 数据库**每日备份**（沿用 OSC 的 `backup-osc.ps1` 思路，改为 `pkb`；**V0.1 是否要做待拍板**）
   - MinIO 对象与 `attachment` 记录的**一致性**：删除 / 失败上传的残留对象，需有清理手段（**V0.1 是否做清理 UI 待拍板**）
4. **安全**：
   - 密码 BCrypt 加密存储
   - 登录图形验证码 + 连续失败 5 次锁定 15 分钟
   - 富文本 / md 双重 XSS 清洗（jsoup + DOMPurify）
   - 附件类型白名单 + 魔数校验
   - Sa-Token Header 鉴权；**接口默认全部要求登录**（除引导页 / 登录页所需接口）
   - ⚠️ **单账号不等于可以不设防**：无权限矩阵意味着**任何拿到 token 的人拥有一切**，故 token 有效期与失效策略需明确
5. **可维护性**：
   - 配置环境变量化（`.env` 不入仓，`.env.example` 入仓）
   - 单一出处：同一事实只写一处
   - 注释与文档使用中文；提交信息全英文 title + 中文 body

## 八、UI/UX 与信息架构

### 8.1 设计基调

1. **低干扰**：首页第一眼是输入框，不是仪表盘
2. **两端各得其所**：桌面用三列并行（信息密度），手机用 3 Tab 串行（拇指可达）
3. **格式可见**：md / html 徽标明确，避免「这条为什么排版不一样」的困惑
4. **不追求花哨**：动效克制，不做无意义过渡

### 8.2 页面地图

| 路由 | 页面 | 外壳 | 说明 |
| :--- | :--- | :--- | :--- |
| `/` | 首页工作台 | AppShell | 桌面三列 / 手机 3 Tab |
| `/notes` | 笔记列表 | AppShell | 全量 + 筛选 |
| `/note/:id` | 笔记全屏页 | AppShell | **手机端主用的详情页**；桌面也可直接访问 |
| `/tags` | 标签管理 | AppShell | `type=0` |
| `/projects` | 项目管理 | AppShell | `type=1` |
| `/login` | 登录页 | PublicLayout（`meta.bare`） | 无页头页脚 |
| `/init` | 引导页 | PublicLayout（`meta.bare`） | 仅未初始化时可达 |

- 外壳只有两套：**`AppShell`**（内部功能）+ **`PublicLayout`**（登录 / 引导）
- **无「管理端 / 成员端」之分**（OSC 的教训：两套外壳互不连通）
- 菜单项**砍到 3~4 项**：笔记 / 项目 / 标签（+ 未来扩展位）

### 8.3 移动端第一体验

- **首页输入框**是移动端的第一体验，必须**常驻、够大、不遮挡**
- 手机不依赖 hover、不用大表格、不做横向滚动
- 详情用**独立路由页**而非抽屉（抽屉在小屏体验差且难返回）

### 8.4 关键体验标准

| 场景 | 标准 |
| :--- | :--- |
| 记录一条想法 | 首页聚焦 → 输入 → 回车，**不跳页**，全程 ≤ 3 秒 |
| 从首页找一条旧笔记 | 输入关键词 → 结果可见，≤ 3 次交互 |
| 归档一条待整理 | 首页「待整理」列点开 → 选项目 / 标签 → 保存，≤ 4 次交互 |
| 手机单手操作 | 主要操作在屏幕下半区（3 Tab）或顶部常驻输入框 |

### C.4 忘记密码重置方式（#10，2026-10-15 拍板）

**决策：采用「文档化步骤」，不写一次性脚本、不做重置接口。**

#### 为什么账号与存储可以解耦（本决策成立的前提）

冻结的 4 张业务表（`note` / `tag` / `note_tag` / `attachment`）**没有任何一张带 `user_id`**，
也没有指向 `user` 的外键。这是单用户系统的直接结果：**「只有一个人」让「归属」这个概念消失了。**

**推论**：**删除账号 ≠ 删除数据。换锁不需要搬屋子。**

#### 首选路径：删账号 → 重走引导页

三步，缺一不可（三步的**命令级细节**见 `README.md`「常见问题」小节）：

1. **硬删 `user` 行** —— ⚠️ 必须**绕过 `@TableLogic`**（`User.isDeleted` 挂了该注解，走 MP 的删除只会置 `is_deleted=1`），故用原生 `DELETE`
2. **清 Redis 里的 Sa-Token session** —— ⚠️ Sa-Token **不查库**，旧 token 在 Redis 里依然有效；不清就会出现「看起来仍登录 → 引导页不出现」而流程走不下去
3. 刷新页面 → 引导页出现 → 重新建号

**选它的理由**：① 不用手算 bcrypt hash（原问题的真正难点）；② 不维护常驻脚本（脚本一定会漂移）；
③ 复用已验证的引导页代码，**零新增代码**；④ `note` 表无 `user_id`，**无任何数据损失**。

#### 备选路径：`UPDATE` 密码

仅在「引导页因某种原因走不通」时使用；文档需**附上生成 bcrypt hash 的完整命令**，照着敲即可。

#### 不选方案及理由（记入文档，避免重复讨论）

- ❌ **一次性脚本**：单用户系统不值得为重置密码维护常驻脚本；若做成接口还有**被误当「后门」**的风险
- ❌ **纯直接改库（无文档）**：每次忘了都要重新摸索一遍

#### ⚠️ 三个坑的处理结论（T3 已实测，详见交接文档 §四）

| 坑 | 结论 |
| :--- | :--- |
| **坑 1** `user` 软删 | `User` 实体**确有** `@TableLogic` → **重置一律用原生 `DELETE`**，不走 MP 删除。✅ 另：引导页判定是 `userMapper.selectCount(null)`，**MP 会自动追加 `is_deleted=0`**，所以**不受软删影响**（原担心的「卡住」不成立） |
| **坑 2** Redis session | 实际 key 前缀为 **`pkb-token:login:token:*`** / `pkb-token:login:session:*`（由 `sa-token.token-name` 决定，**不是** `pkb:login:token:*`）。⚠️ Redis 里另有大量归档项目遗留的 `osc-token:*` key，清理时**不要误删** |
| **坑 3** `user` 表未简化 | ✅ **T1 已完成**（7 列）；`constants/roles.js` 整删、`StpInterfaceImpl` 已删、强制改密逻辑已删 |

## 附录 D：关键决策溯源记录

> 记录**已拍板**决策的理由与**被否决的备选方案**，避免后续重复讨论。
> 编号 `D-xx` 为本 PRD 内部编号；《开发任务点清单》§6 为**实现层决策**的单一出处。

### D-1 一条笔记一种格式：为什么不双存

**决策**：`content_format` 新建时选定、之后不切换，默认 md。

**否决备选**：
- 「双列镜像存 md + html」→ **双份存储、双份清洗，一定漂移**（改了 md 忘了同步 html）
- 「只存 md、富文本实时转」→ **转换有损**，表格 / 嵌套列表会丢

**代价**：使用者必须在建笔记时想清楚格式。**接受理由**：格式其实是「这条笔记是技术笔记还是排版文档」的自然属性，多数情况下不需要纠结。

### D-2 项目 = `tag.type=1`：为什么不独立建表

**决策**：项目与标签共用 `tag` 表，靠 `type` 区分；表结构多对多，**UI 约束项目单选**。

**否决备选**：
- 「项目独立建表」→ V0.1 用不上项目元信息（起止时间 / 状态 / 进度），**过度设计**
- 「`note.parent_id` 自关联」→ 项目**既是笔记又是容器**，语义混乱

**代价**：数据层不天然保证「一条笔记一个项目」。**接受理由 + 兜底**：后端关联写入时替换而非新增（见 P-006）。

### D-3 `content_text` 独立成列：为什么不用 `content` 直接搜

**决策**：md 存轻量去标记文本，html 由 jsoup 剥标签得到；**搜索只打 `title + content_text`，永不打 `content`**。

**理由**：直接搜 `content` 会命中 html 标签名（`span` / `div`）与 markdown 符号（`#` / `*`），产生**大量误召回**，且误召回会随笔记增多而恶化。

**代价**：多一列、多一道同步逻辑（R1 风险）。**接受理由**：搜索正确性是这个系统的核心价值，值得多一列。

### D-4 `pinned` 保留

**决策**：`note.pinned` 明确保留，参与排序 `pinned DESC, updated_at DESC`。

**理由**：用户明确要求保留。置顶是自用系统里最省事的「重要性标记」，不依赖标签体系。

### D-5 V0.1 不搜标签名

**决策**：搜索范围只含标题 + 正文；搜标签名留给后续版本。

**理由**：V0.1 先保证核心检索可靠；标签检索的交互（是加筛选还是并入关键词）需要真实使用数据才能判断。

### D-6 首页三列各自滚动

**决策**：桌面首页三列**各自滚动**；外壳 `height:100% + overflow:hidden`；`min-height:0` 逐层加。

**理由**：三列各自滚动才能「一屏看三块」，整页滚动会让底部的列被推走。**代价**：flex 嵌套滚动很脆，`min-height:0` 漏一层就失效（OSC 已踩过）。

### D-7 手机端详情用独立路由页而非抽屉

**决策**：桌面 `el-drawer`（~720px），手机 `/note/:id` 独立全屏页；**两处复用同一份表单组件**。

**理由**：小屏抽屉挤压正文、返回手势不自然；独立页可用浏览器返回键。**代价**：两处载体，必须靠「共用一份表单组件」防漂移。

### D-8 单账号 + 删权限矩阵

**决策**：只建一个账号；`constants/roles.js` 整删；守卫只判登录态 + 初始化态；强制改密删除；图形验证码保留。

**理由**：唯一用户是自己，权限矩阵是纯负资产。**代价**：未来若要多人共用，需重新设计（但表结构允许加行，不算死路）。

### D-9 保留 FastExcel 与 ECharts 但 V0.1 不启用

**决策**：代码**保留不动、不删不改**，V0.1 不启用。

**理由**：**用户明确拍板** —— 未来极可能用上（导出笔记、看知识增长曲线）。**代价**：工程里带着两个不用的依赖；**接受理由**：删了以后要回来，成本远大于留着。

### D-10 V0.1 不做上线部署

**决策**：本机 / 局域网自用，无公网、无多实例；**文档不含「上线部署」章节**。

**理由**：自用系统不需要；过早引入部署复杂度会挤占核心功能的时间。
